# Interface audit and redesign

| Area           | Existing problem                                                        | Redesign                                                                                                              |
| -------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Navigation     | Seven destinations, a heavy embedded tracker, small mobile labels       | Five main sections; Drive in Settings; global timer in header; mobile navigation wraps within the viewport            |
| Dashboard      | Tracker statistics and decorative panels competed with study tasks      | Recent sessions, recently studied and pinned sets, folders, recent transcripts and tests; three creation entry points |
| Library        | Each tile repeated three study buttons plus other controls              | Clear title, folder, term/star counts, mastery and study date; Open set plus an accessible disclosure for modes       |
| Set editor     | Dense action rows; extras mixed with everyday tasks                     | Consistent controls and spacing; responsive term/definition rows; secondary actions in disclosures                    |
| Flashcards     | Inconsistent surfaces, small labels, cramped controls                   | Centered dominant card, wrapping long definitions, larger controls and shared theme tokens                            |
| Learn          | Configuration obscured the question; incomplete dark feedback           | Advanced question/grade settings collapse; stable question surface; semantic success/error colors                     |
| Test           | Small question navigator targets; results lacked consistent hierarchy   | 44px navigation targets, clear exam controls and readable result rows; independent exam deadline retained             |
| Transcriptions | Providers, keys, server health and generation controls crowded the page | Capture, languages, original/translated segments and saved lessons; quality/models in disclosures; local processing   |
| Settings       | Theme and backend configuration were coupled                            | Appearance, optional Drive, model downloads and device storage; no inference credentials                              |
| Dialogs        | Dense content and inconsistent dimensions                               | Shared modal sizing, scrolling and sticky actions; controls remain keyboard accessible                                |
| Timer          | Bound to the removed tracker                                            | Independent timestamp module; header readout and compact panel; reserved layout space while expanded                  |

## Design system

CSS custom properties define complete light and dark palettes, body/secondary text, surfaces, success/error/warning states, focus, control height and radii. Spacing uses 4/8/12/16/24/32/48px. Common controls are at least 44px high. The saved theme is applied in the document head; System listens for OS changes.

The redesign follows task hierarchy, visible status, editable results, consistent components and keyboard focus. References: [Quizlet Flashcards](https://help.quizlet.com/hc/en-ca/articles/360030988091-Studying-with-Flashcards), [Material foundations](https://m3.material.io/foundations/), [NN/G usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/), [W3C design guidance](https://www.w3.org/WAI/tips/designing/), and [WCAG 2.2](https://www.w3.org/TR/WCAG22/). No branded assets or proprietary layouts were copied. AnkiWeb was reviewed as a simple study-library reference.

See VERIFICATION.md for executed browser checks and remaining hardware limits. Automated layout checks are not a full accessibility certification.

## Study Library as a file manager

Before designing, current guidance for file/folder interfaces and drag-and-drop was read (sources below; the NN/g drag-and-drop article could not be retrieved, so nothing is attributed to it). Decisions:

1. **Dragging is never the only way.** [WCAG 2.2 SC 2.5.7 Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) (Level AA) requires every drag operation to be achievable with a single pointer without dragging, and its "Move to" menu example, technique [G219](https://www.w3.org/WAI/WCAG22/Techniques/general/G219) (a "Move selected items to" drop-down) and [Apple's Human Interface Guidelines for drag and drop](https://developer.apple.com/design/human-interface-guidelines/drag-and-drop) (offer menu commands as alternatives; the Apple page is script-rendered, so this point and the move-versus-copy rule below come from a search summary of it rather than a direct read) say the same. Keyboard operation is a separate requirement. Implemented: a **Move** button on every set tile and folder card, **Move selected to…** for a selection, **Move to…** and Shift+M in the tree, all opening one dialog with a "Destination folder" select (a folder's list excludes itself and its subfolders).
2. **Name the item in every control.** [Atlassian's drag-and-drop accessibility guidelines](https://atlassian.design/components/pragmatic-drag-and-drop/accessibility-guidelines/) ask for a menu trigger per item with a specific name ("Move task 'clean dishes'…"). Buttons are labelled "Move Verbs to a folder…".
3. **Announce and restore focus.** The same page asks for announcements that contain the item name and place, and for focus to return to the trigger or a sensible nearby element. The polite live-region toast says "Moved “Food” to “Spanish”." (or "Moved 2 sets to …"); focus goes to the moved item, or the page heading if it left the view.
4. **Tree semantics and keys follow the [WAI-ARIA Authoring Practices tree view pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/)**: `tree`/`treeitem`/`group`, `aria-expanded` on folders only, `aria-level/setsize/posinset`, `aria-multiselectable` with Space toggling selection (the recommended multi-select model, so selection does not follow focus), one tab stop (roving tabindex), ↑ ↓ → ← Home End, Enter, type-ahead and `*`. Actions for the focused or selected rows are in an ordinary button bar above the tree rather than as controls inside tree items.
5. **Visual feedback on drag** follows [Atlassian's design guidelines](https://atlassian.design/components/pragmatic-drag-and-drop/design-guidelines) and [Cloudscape's drag-and-drop pattern](https://cloudscape.design/patterns/general/drag-and-drop/): a grab cursor, the dragged item dimmed, a highlighted target only where a drop is allowed (not into the current folder, never a folder into itself), a drag preview that shows a count for several items, and a collapsed tree folder that opens after about half a second of hovering (Atlassian suggests 500 ms).
6. **Move, not copy.** Dropping within the same container moves, as in Apple's guidance; there is no copy gesture. Cards, progress, stars and history stay with the set; only its folder changes. Duplicate remains a separate command.
7. **Grid and tree show the same information.** The switch names its destinations ("Grid", "Folder tree", `aria-pressed`) and the choice is remembered. Like a file manager, a folder shows what is directly inside it, with **Include subfolders** to flatten; searching and filtering look through everything below the current folder (everything, from the top level). A breadcrumb path doubles as drop targets, and **Go to folder** is a plain dropdown.
8. **No new Undo.** The request limits Undo to the card editor, so a move is reversed by moving the item back (the confirmation says where it went). Touch devices differ in whether the browser starts a drag from a long press; the Move buttons are the dependable route there and were not tested on a physical touch screen.
